5Defect records

A-05 P1 SEVERE P0 CANDIDATE

Filled order reported as Order Failed; one confirmation produced a success and a failure

Component
Perps order ticket, confirmation dialog, order status toasts
Preconditions
Registered Phoenix trader. Cross margin, USD 10 collateral. Open SOL-PERP long of 0.01 SOL.
Steps
  1. Open SOL-PERP. Select Short, Market.
  2. Enter size 1.2 USD (0.012 SOL), equal to the order that opened the long.
  3. Tap Short SOL, then tap Place Short once.
  4. Watch the toast area and the Positions tab for 10 s.
Expected
One submission, one status. A success toast with the transaction, and a positions table that matches it.
Actual
Place Short tapped once at 01:34.8. Market Order Placed toast for Short 0.0120 SOL with transaction 5h9V...jjLG at 01:35.7. At 01:36.0 an Order Failed toast for the same order stacks over it and remains alone on screen until 01:44.75, reading Phoenix trader state 429. The long position is closed: Positions (1) becomes Positions (0). The user, reading the failure, raised the size to 1.3 USD at 02:04 and opened a new, unintended short of 0.01 SOL (G78X...WzHQ).
Frequency
1 of 1 opposite-side order observed. The 429 suggests timing dependence.
Root cause
Hypothesis A: the confirm handler dispatches the order twice, for example a click handler plus form submit, or an effect that re-runs. The second request is rejected with HTTP 429. Hypothesis B: the post-fill trader state refresh is rate limited, and any error in the chain is mapped to Order Failed for the same order. Both are consistent with a success and a failure arriving 0.3 s apart. A-13 shows the same 429 on trader state reads the next day, which favors hypothesis B as at least part of the cause.
Risk
Under A, the only thing that stopped a duplicate real order was the rate limit; without it the outcome meets P0. Under B, the venue tells users a filled order failed, which drives retries and unintended positions, as happened here.
Recommendation
1. Generate a client order ID when the dialog opens; send it with the order and reject reuse server side. 2. Disable the confirm button from first tap until a terminal status. 3. Key toasts by client order ID so a later event cannot overwrite a fill. 4. Separate order errors from refresh errors; a failed refresh must read "Filled. Refreshing positions" and retry with backoff on 429. 5. Treat the transaction signature as the source of truth for status.
Verification needed
Trade History for 22:10 to 22:11 device time. Two submissions for Short 0.012 confirm hypothesis A and raise severity to P0.
A-01 P1 SEVERE UPDATED REV 4

Buy action remains enabled after insufficient balance warning

Component
Spot order panel, Buy tab, primary action control, Solana (Jupiter) route
Preconditions
Wallet connected. USDC balance below the entered notional.
Steps
  1. Open a Solana spot pair, for example Tulip.
  2. Select the Buy tab.
  3. Enter an amount exceeding the USDC balance, or tap the 50 USD preset.
  4. Observe the warning line and the primary action control.
  5. Repeat on an Arbitrum pair routed by Relay.
Expected
Primary action disabled while the shortfall warning is displayed, on every route.
Actual
Jupiter route: warning Not enough USDC - you have 13.8 USDC; Buy Tulip renders enabled. Relay route (ETH on Arbitrum): warning Not enough USD - largest origin is 13.8 on Solana USDC; Buy ETH is correctly disabled.
Frequency
3 of 3 on the Jupiter route: USDC 0 (Rec0 00:00), USDC 13.8 (Rec0 01:30), USDC 13.8 on Tulip (Rec1 00:00 to 00:12). Also seen on USDT (Rec4 00:04). 0 of 1 on the Relay route.
Root cause
Hypothesis, narrowed by rev 4: the Relay path binds its shortfall check to the disabled state; the Jupiter path binds it to the warning text only. The fix pattern already exists in the codebase.
Risk
Submission of an unfundable order. If a partial fill or fee-only transaction settles, the outcome meets the P0 incorrect deduction definition.
Recommendation
Move the shortfall predicate into a route-independent canSubmit used by both paths. Add a regression assertion that the control is disabled whenever the warning node is mounted, parameterised by route.
A-06 P1 SEVERE

Order confirmation and toast show 0.0120 SOL; position fills 0.01 SOL

Component
Perps order ticket size conversion, confirmation dialog, fill toast
Preconditions
Registered trader with collateral. SOL-PERP.
Steps
  1. Enter size 1.2 USD on SOL-PERP Long.
  2. Read the confirmation dialog, then tap Place Long.
  3. Read the Market Order Placed toast.
  4. Read Size and Position Value in the Positions tab.
Expected
The dialog shows the size that will fill after lot rounding, and the toast matches the fill.
Actual
Dialog: Long 0.012 SOL at $100.34, order value USD 1.20. Toast: Size 0.0120 ($1.20). Position: 0.01 SOL, value USD 1.00. The later 1.3 USD short (0.013 SOL) also filled as 0.01 SOL.
Frequency
3 of 3 orders in Rec5.
Root cause
Hypothesis: the ticket converts USD to base units at full precision and the market lot size (0.01 SOL) is applied on chain. The UI never reads back the lot size.
Risk
Order size is misreported by up to 20 percent at these notionals, and the rounding is invisible. It is also why a 0.012 short closed the long exactly in A-05: both were really 0.01.
Recommendation
Round the entered size to the market lot size before quoting, show Fills as 0.01 SOL (lot 0.01) under the input, and build the toast from the fill event, not the request.
A-02 P2 MEDIUM UPDATED REV 4

Max selects full native balance; raw error Jupiter quote 400; no reason shown

Component
Spot order panel, Sell tab, percentage presets, quote error handling
Preconditions
Wallet holds native SOL only. No wrapped SOL.
Steps
  1. Open the SOL spot pair and select the Sell tab.
  2. Tap Max.
  3. Wait for the quote to resolve and attempt to submit.
  4. Tap 75 percent and wait again.
Expected
Max reserves rent and network fees. Any quote failure is explained in plain language with the action to take.
Actual
Rec0: Max fills 0.137792 SOL; quote resolves; Sell disabled for 14 s with no message; 75 percent works. Rec1: Max fills 0.063742 SOL; quote fields stay blank and the panel prints the raw string Jupiter quote 400. The condition persists into Rec2 00:00 to 00:28, including at 25 percent.
Frequency
2 of 2 sessions. Symptom differs by balance: disabled button at 0.137 SOL, HTTP 400 at 0.064 SOL.
Root cause
Hypothesis: Max uses the raw lamport balance with no reserve. With less headroom the quote request itself is rejected by the aggregator with HTTP 400, and the status code is shown verbatim. The persistence at 25 percent suggests the failed quote is cached rather than re-requested when the amount changes.
Risk
The primary sell control dead-ends for any user who sells everything, which is the common exit action. Raw HTTP codes read as a broken venue.
Recommendation
1. Max fills balance - rentExempt - feeBuffer, about 0.003 SOL. 2. Map aggregator errors to messages, for example Keep about 0.003 SOL for network fees. 3. Invalidate the quote cache on every amount change. 4. Show the reason whenever the control is disabled.
A-03 P2 MEDIUM

Quote service returns no data while price chart continues updating

Component
Trades feed, quote service, order panel
Preconditions
Continuous interaction on a SOL spot pair for 60 to 90 s.
Steps
  1. Remain on the pair through sustained interaction.
  2. Observe the Trades panel header.
  3. Change the order amount and observe the quote fields.
Expected
Degraded service is communicated consistently across every dependent panel, with a retry path.
Actual
Trades panel shows a DEGRADED badge over No data yet. Order panel renders a dash for receive amount, price impact and router, and refuses submission. Candlestick chart and ticker strip continue updating normally.
Frequency
Once in Rec0, after 60 to 90 s of continuous interaction. Not re-observed on 13 Sep.
Root cause
Hypothesis: trades stream and quote endpoint share a backend or rate limit that the chart feed does not. A degraded state exists for the trades panel but not for the order panel, so an outage renders as placeholder dashes, indistinguishable from the empty-input state.
Risk
A live chart is read as evidence the venue is healthy. Conflicting signals during price movement contribute to mistimed exits and to disputes attributed to fills rather than feeds.
Recommendation
Propagate a single venue-health state to all dependent panels. When quotes are unavailable, state so explicitly and offer retry. Add retry with backoff on the quote subscription.
A-04 P3 MINOR

Balance display lags swap confirmation by approximately 8 s

Component
Balance display, swap confirmation handler
Steps
  1. Execute a spot sell.
  2. On the success toast, read the balance rows.
  3. Wait for the next poll interval.
Expected
Balances reflect the settled trade when confirmation is displayed, or show an explicit pending state.
Actual
Swap Success toast displays with signature while balances still read 0.2 SOL and 0 USDC. Updated values (0.148077 SOL, 5.15 USDC) appear approximately 8 s later.
Frequency
2 of 2 swaps in Rec0. First swap: toast 00:22, balance 00:30 (about 8 s). Second swap of 0.01 SOL, submitted at 00:30 while the balance was still stale: toast 00:31, balance 00:41 (about 10 s).
Root cause
Hypothesis: balances are sourced from a fixed-interval poll that is not invalidated on swap confirmation.
Risk
Users resubmit when figures do not update. Combined with A-01, which leaves the action enabled, this permits a duplicate real order. That outcome meets the P0 definition.
Recommendation
Invalidate and refetch the balance query in the swap confirmation handler. Display an optimistic pending value in the interim.
A-13 P2 MEDIUM

Trader state request rate limited (429); account shown as unverified with zero balance and no automatic retry

Component
Perps trader state loading, positions tab, order ticket
Preconditions
Registered trader with USD 10 collateral and one open position. Perps page open, ETH-PERP.
Steps
  1. Open a perps market while registered, with collateral and an open position.
  2. Stay on the page, or switch markets a few times.
  3. Read the Positions tab and the order ticket.
  4. Wait without touching Retry and note whether the state recovers.
Expected
A transient 429 is retried automatically with backoff. Last known positions and balance stay on screen, marked as refreshing.
Actual
00:46:49: the positions area reads Could not verify Phoenix registration. Phoenix trader state 429 with a Retry link. At the same moment the ticket falls back to the unregistered state: Deposit USDC to trade, Available to Trade $0.00, Positions (0), order leverage blank. 00:46:57: the state is back, Available to Trade $9.95, Positions (1), leverage 25.0x. The screenshots do not show whether Retry was tapped; the tester reports the page does not refresh on its own and positions are often unreadable.
Frequency
Reported as frequent by the tester. 2 captures on 14 Sep 2026, at 00:46 and 13:57 (mobile layout, filter All). The same 429 appears in A-05 (Rec5 01:36) on a different day.
Root cause
The trader state endpoint (or the RPC behind it) is rate limited, and the client treats the failed read as "not registered, no collateral, no positions" instead of "unknown". No automatic retry is scheduled. The recurrence on 13 and 14 September makes this the likely common cause behind A-05 hypothesis B.
Risk
During the error the account shows zero balance and zero positions while a leveraged position is open, so the user cannot monitor or close it. A user who believes the account is unregistered may register or deposit again. Workaround: Retry or reload.
Recommendation
1. Keep the last successful trader state and show it as stale with a timestamp; never substitute zeros for an unknown. 2. Retry 429 automatically with exponential backoff and jitter, honoring Retry-After. 3. Deduplicate and cache trader state reads across components (one request per wallet per interval), and prefer a websocket or account subscription over polling. 4. Keep order entry for closing positions available from the cached state.
A-07 P2 MEDIUM

Perps market list fetch failure shown as an empty category

Component
Perps left panel market list, market header
Preconditions
Perps page open for more than 60 s, switching markets.
Steps
  1. Open Perps with the All category selected.
  2. Switch between markets, for example SOL-PERP to AAPL-PERP.
  3. Watch the market list and the Mark, Index and Funding fields.
Expected
A loading or error state with a retry, and the previous list kept until new data arrives.
Actual
At Rec2 01:56 the list is populated. By 02:00 the All category reads No markets in this category. and the header shows blank Mark, Index and Funding. The tester reports that on other occasions the panel prints an API error; that text was not captured in these recordings.
Frequency

A-08 P2 MEDIUM

Trader registration stalls on Registering until the page is reloaded

Component
Perps onboarding, Register as a Phoenix trader
Preconditions
Wallet not yet registered. At least 0.02 SOL available for account rent.
Steps
  1. Open any perps market. Tap Register.
  2. Wait with the page open.
  3. Reload the page and tap Register again.
Expected
Registration completes, or fails with a reason and a retry, within a bounded time.
Actual
Rec3: the button reads Registering... from 00:36 until the recording ends at 01:02, with no progress or error. The tester reports it stayed that way for hours. After a reload (Rec5) registration completes in about 5 s and the toast Trader registered appears at 00:19.
Frequency
1 of 1 first attempt stalled; 1 of 1 attempt after reload succeeded.
Root cause
Hypothesis: the client waits for a confirmation event that was missed, or the transaction was never sent, and there is no timeout. After reload the account lookup finds the finished or pending state.
Risk
Perps is unreachable for a first-time user until they guess to reload. Rent may already be paid.
Recommendation
Poll the account address after sending, time out at about 30 s, then show the signature with "Check again" and "Retry". On load, detect an existing trader account before offering Register.

A-10 P2 MEDIUM

Positions tab reads Positions (1) while listing No positions

Component
Perps positions table, market filter
Preconditions
One open position on a market other than the one being viewed.
Steps
  1. Open a SOL-PERP position.
  2. Navigate to ETH-PERP.
  3. Read the Positions tab label and the table.
Expected
Count and list agree, or the filter reads "1 position on other markets. Show all".
Actual
Label Positions (1); filter defaults to ETH; table reads No positions. Selecting Both shows the SOL-PERP short.

Deterministic, follows from the filter default.

A-11 P2 MEDIUM

Perps chart has no candle interval selector or label

Component
Perps chart toolbar and time axis
Steps
  1. Open a spot pair and note the interval buttons above the chart.
  2. Open SOL-PERP.
  3. Look for an interval control; collapse and expand the sidebar; tap a candle.
Expected
Interval selector and visible interval on perps, at least matching spot. Crosshair shows date and time.
Actual
Spot shows 1M 5M 15M 1H 4H 1D. Perps shows none, and no interval label. The time axis repeats the day number (13 13 13 13) with no time of day, and tapping a candle shows the date only. Toggling the sidebar does not reveal a toolbar.
Frequency
Always. All perps markets observed.
Root cause
Hypothesis: the perps chart is a separate component that fixes the interval and uses a date-only tick formatter.

Recommendation
Reuse the spot interval control on perps, show the active interval in the chart legend, and format ticks and crosshair as date plus HH:mm below 1D.

6Improvement proposals

Not defects. Filed separately for product review.

I-01
Take profit and stop loss on the ticket. The perps ticket offers Market, Limit and Reduce only; there is no way to attach TP or SL at entry. Proposal: TP and SL fields at entry and on open positions, plus staged partial take profit (for example TP1 30 percent, TP2 30 percent, TP3 40 percent) that must sum to 100 percent, each placed as a reduce-only trigger so the position cannot flip. After TP1 fills, offer to move SL to entry.
I-02
Position lines on the chart. With a SOL-PERP long open at 100.36 and the SOL-PERP chart on screen (Rec5 01:12), the chart shows no entry or order line; the only record is the table below it. Proposal: entry, TP, SL and liquidation price lines colored by side, draggable for TP and SL, with a one-tap Close button on the entry line so a position can be closed directly from the chart.
I-03
Resulting position in the confirmation. Perps positions net per market, so an opposite order of equal size closes the position. The dialog in Rec5 01:33 did not say so. Proposal: a line such as Closes your 0.01 SOL long. Resulting position: none. This would also have exposed A-05 and A-06 immediately.
I-04
Execution latency. Measured in Rec5 at 4 fps: Place Short tapped at 01:34.8, Market Order Placed at 01:35.7, about 0.9 s to 1.2 s on screen. The tester reports over 1.2 s on other orders. Proposal: publish p50 and p95 targets, show fill time in the toast, and render an optimistic pending row within 100 ms while settlement completes.
I-05
Order book depth. Screenshot 22:14 shows depth bars scaled per level: 226.951 and 119.416 are visible while levels of 3 to 45 almost vanish, and the Size column has no unit. Proposal: cumulative depth bars, a unit in the header with a base or USD toggle, and a spread row between bids and asks.
I-06
Collateral purpose on screen. The Collateral block shows available amount and a Swap and deposit action but not what the collateral secures. In cross mode one pool backs every position, so a loss on one position reduces margin for all. Proposal: one line under Collateral, for example Backs all cross positions, plus Used and Free figures per position in the positions table.
I-07
Explain isolated-only markets at the badge. GOLD, SILVER and COPPER carry an ISO badge in the market list; the reason appears only inside the ticket (Rec3 00:08). Proposal: a tooltip on the badge with the same text, so the constraint is known before the market is opened.
I-08
Explain registration before the tap. The Register button follows "needs ~0.02 SOL for rent and fees" but does not say that trading perps requires a one-time on-chain Phoenix trader account. Proposal: a short explainer and the exact cost in the confirmation, shown once per wallet.
I-09
Distinguish market trades from own trades. The Trades tab beside the order book lists all market trades, while own fills sit under Trade History. The two names are close. Proposal: rename to Market trades and My trades, and add a venue label, for example "Phoenix", to the market tape.
I-10
Full-screen chart with analysis tools. The chart offers price and time only, with no indicators or drawing tools, and no full-screen mode. Proposal: a full-screen view with core indicators (volume, moving averages, RSI) and basic drawing (horizontal line, trend line), either through a licensed charting library or a built-in subset.
I-11
Guide holders of other assets into perps. Perps accepts USDC. A wallet holding USDT and SOL (Rec2 01:20) sees "Deposit USDC to trade" without being told that its USDT and SOL can be converted in one step. Proposal: when USDC is short, show "You hold 2 USDT and 0.06 SOL. Swap and deposit" as the primary action on the ticket.

7Confirmed working

O-01
No wallet prompt per trade. Registration, collateral deposit, long, short and close all executed from in-app buttons with no signature popup (Rec5 00:19 to 02:14). This removes the main friction of on-chain trading and should be kept as a regression baseline.
O-02
Relay route shortfall handling. The cross-chain route disables Buy and explains where funds sit (Rec1 00:56). It is the reference behavior for A-01.
